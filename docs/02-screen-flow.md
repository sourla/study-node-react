# 시나리오 2 — 화면 개발 플로우 한 바퀴: 상세페이지 댓글

브랜치 `feat/comments`. 과제는 `00-scenarios.md`. 범위는 정적 JSON 읽기만, 쓰기 없음.

## 시도 1 — 별도 댓글 페이지 + 코드 안의 정적 배열 (커밋 `875e57b`)

**만든 것.** `/csr/:id/comments`, `/ssr/:id/comments` 페이지 둘, `CommentList`, 상세 화면의 "댓글 보기" 링크, 테스트 6개. 테스트와 lint는 통과했다.

**왜 다시 했나.**

- 댓글 데이터가 페이지 코드 안의 배열이라 "어디서 가져오나"가 사라졌다. CSR 페이지와 SSR 페이지가 이름만 다르고 동작이 같았고, SSR 페이지에는 loader가 없었다.
- 별도 페이지로 빼면서 "상세 loader가 게시글과 댓글을 어떻게 합쳐 오나"라는 질문이 아예 생기지 않았다.
- `comments.map(c => ({ ...c, postId: Number(id) }))`는 필터가 아니라 덮어쓰기라 어떤 게시글이든 같은 댓글이 붙었다. 댓글 없는 게시글이 존재할 수 없어 빈 상태를 겪을 길이 없었다.
- `key={comment.postId}`라 같은 게시글의 댓글끼리 key가 겹쳤다.

**배운 것.** 쉬운 길을 고르면 시나리오가 묻던 결정이 조용히 사라진다. 결정할 게 안 생기면 의심해야 한다.

## 시도 2 — 상세 페이지 아래에 붙이고, 데이터는 JSON에서

### 1. 데이터

`public/data/comments.json`. `postId`로 게시글과 연결. 게시글 4, 5는 댓글이 없다(빈 상태를 강제로 겪기 위해).

### 2. 스키마와 타입

`common/schemas/comment.ts`에 `commentSchema`(`createdAt`은 `z.iso.datetime()`), `common/types/comment.ts`에 `Comment`. 시도 1의 `updatedAt`은 쓰는 곳이 없어 뺐다.

### 3. 조회 — 코드 전에 정한 결정 셋

| 결정                          | 선택                                | 이유                                                                 |
| ----------------------------- | ----------------------------------- | -------------------------------------------------------------------- |
| 게시글과 댓글을 어떻게 합치나 | `Promise.all`로 병렬                | 순차로 하면 서버에서 왕복이 두 번                                    |
| 댓글 조회가 실패하면          | 페이지 전체 실패 (`throw Response`) | 단순함 우선. 7단계에서 다시 본다                                     |
| loader 반환 형태              | `{ post, comments }`                | `SsrDetailPage`의 `useLoaderData` 모양이 바뀌므로 테스트도 같이 고침 |

- SSR: `ssrDetailLoader`가 두 JSON을 병렬로 받아 검증하고 합친다. 서버 로그는 `응답 수신 200 200` → `데이터 반환 1 댓글 2`.
- CSR: `common/api/comments.ts`의 `fetchComments`. `CsrDetailPage`가 `useEffect`에서 `Promise.all([fetchPost, fetchComments])`.
- **발견.** 기존 `CsrDetailPage`에 에러 처리가 없었다. 조회가 실패하면 "불러오는 중"이 영원히 남는다. 과제의 관찰 질문("CSR 상세에서 조회가 실패하면 화면은?")이 이걸 겨냥한 것이었다. `error` state와 `role="alert"`를 추가했다.

### 4. 컴포넌트

`CommentList`: 헤딩 "댓글 N", 빈 상태 문구 "아직 댓글이 없습니다.", `key={comment.id}`. 두 상세 페이지가 `PostDetail` 아래에 그대로 배치한다.

**관찰 질문 답.** 댓글 날짜를 그리는 순간 시나리오 1의 과제 B가 그대로 다시 나타난다. 시나리오 1의 결론대로 `common/utils/formatDate.ts`에 로케일과 타임존을 고정하고 `CommentList`, `PostList`, `PostDetail`이 모두 이걸 쓰게 했다. 이 브랜치는 `main`에서 갈라져 그 버그가 살아 있었기 때문에, 새 화면을 붙이는 김에 같이 잡은 셈이다.

### 5. 테스트 (13 파일, 28개)

- `comments.test.ts` 4개: 필터, 빈 배열, 응답 오류, 형식 오류
- `ssrDetailLoader.test.ts` 5개: 합치기, 빈 댓글, 404, 503, 댓글 형식 오류
- `CommentList.test.tsx` 2개: 목록, 빈 상태
- `CsrDetailPage.test.tsx` 3개: 렌더, 빈 상태, 댓글 실패 시 alert
- `SsrDetailPage.test.tsx` 1개: `createMemoryRouter` loader로 주입
- `formatDate.test.ts` 2개

포인트 하나. fetch가 두 URL을 부르므로 mock을 `mockResolvedValue` 하나로 못 쓴다. `mockImplementation`에서 URL에 `comments`가 있는지로 분기했다.

### 6. 브라우저 확인

| 관찰                 | `/csr/1`                                                            | `/ssr/1`                                                             |
| -------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `curl`로 받은 HTML   | "불러오는 중"                                                       | 게시글 + 댓글 2개 + "댓글 2", 날짜 `2026년 9월 1일`                  |
| 브라우저 데이터 요청 | `posts.json`, `comments.json` 두 개                                 | 없음 (`__manifest`만)                                                |
| 브라우저 콘솔        | `[page] useEffect` → `[api] fetchPost/fetchComments 시작·응답·완료` | 에러 0 (hydration 깨끗)                                              |
| 서버 터미널          | 없음                                                                | `[route loader] /ssr/:id 응답 수신 200 200` → `데이터 반환 1 댓글 2` |

- `/ssr/1.data`(클라이언트 전환 시 응답)에 `"comments"` 키와 댓글 본문이 들어 있다. 댓글이 별도 요청이 아니라 loader 데이터의 일부로 온다.
- `/ssr/4`는 서버 HTML에 "아직 댓글이 없습니다."가 이미 들어 있다.

### 7. 디버깅 적용 — 댓글 한 건 깨뜨리기

`comments.json`의 id 4(게시글 3의 댓글) `createdAt`을 `"2026-09-03"`으로 바꿨다.

|             | `/csr/3`                                                               | `/ssr/3`                      | `/ssr/1` | `/ssr/4` (댓글 없음) |
| ----------- | ---------------------------------------------------------------------- | ----------------------------- | -------- | -------------------- |
| HTTP        | 200                                                                    | 500                           | 500      | 500                  |
| 화면        | 헤더 + alert "댓글 데이터 형식이 올바르지 않습니다.", 게시글 본문 없음 | `ErrorBoundary`               | 같음     | 같음                 |
| 서버 터미널 | 없음                                                                   | `응답 수신 200 200` 이후 없음 |          |                      |

**게시글까지 안 보이나?** 그렇다. 양쪽 다. CSR은 `Promise.all`이 하나라도 실패하면 `catch`로 가고, SSR은 loader가 던진다. 댓글이 하나도 없는 게시글 4까지 500이다. 파일 전체를 검증하기 때문이다.

**그게 원하는 동작인가?** 아니다. 댓글은 부가 정보라 게시글은 보여야 한다. 선택지는 셋이고 이 브랜치에서는 적용하지 않고 기록만 남긴다.

1. 댓글 조회 실패는 빈 배열로 대체하고 경고만 남긴다.
2. 레코드 단위로 검증해 깨진 댓글만 뺀다.
3. CSR은 `Promise.allSettled`로 바꿔 게시글만이라도 그린다.

서버 로그에는 실패 흔적이 없다. 시나리오 1에서 본 것과 같다. HTTP 상태로 본다.

## 정리

화면 하나를 붙이는 흐름은 결국 이 순서였다. 데이터 → 스키마 → 조회(loader와 fetch, 여기서 결정이 생긴다) → 컴포넌트 → 페이지 연결 → 테스트 → 브라우저에서 두 경로 비교 → 일부러 깨뜨려 보기.

|               | 시도 1             | 시도 2                                |
| ------------- | ------------------ | ------------------------------------- |
| 데이터 출처   | 페이지 코드 안     | `public/data/comments.json`           |
| SSR loader    | 없음               | 게시글과 댓글 병렬 조회 후 합침       |
| CSR fetch     | 없음               | `fetchComments` + `Promise.all`       |
| 빈 상태       | 겪을 수 없음       | 게시글 4, 5에서 안내 문구             |
| CSR 실패 처리 | 없음 (영원한 로딩) | alert                                 |
| 테스트        | 6개, 하드코딩 확인 | 17개 추가, 조회 경로와 실패 경로 포함 |
