# 시나리오 과제

이 레포의 `main`은 뼈대다. 시나리오는 `main`에서 브랜치를 따서 풀고, 풀이는 브랜치에 남긴다(`main`에 머지하지 않는다).

| 브랜치                     | 역할                                    |
| -------------------------- | --------------------------------------- |
| `main`                     | 뼈대 + 이 과제 정의                     |
| `debug/render-flow-answer` | 시나리오 1 풀이                         |
| `feat/comments`            | 시나리오 2 풀이                         |
| `debug/render-flow`        | 시나리오 1 참고 풀이. 다 푼 뒤에 비교용 |

공통 도구는 셋이면 충분하다. dev 서버 터미널(stdout), 브라우저 콘솔·네트워크 탭, `curl`. 코드의 로그 접두어로 **어디서 실행됐는지** 구분한다.

| 접두어            | 실행 위치 | 보는 곳         |
| ----------------- | --------- | --------------- |
| `[route loader]`  | 서버      | dev 서버 터미널 |
| `[api]`, `[page]` | 브라우저  | 브라우저 콘솔   |

## 시나리오 1 — CSR vs SSR 흐름 이해와 디버깅 (`debug/render-flow-answer`)

목표: 같은 게시글 화면이 `/csr`과 `/ssr`에서 어떻게 다르게 만들어지는지 눈으로 확인하고, 실제 버그 하나를 찾아 고친다.

### 과제 A. 흐름 관찰

1. **첫 요청** (주소창 입력 / 새로고침). `/csr`과 `/ssr` 각각에 대해 네 가지를 기록해 표로 만든다.
   - `curl -s http://localhost:5173/<경로>`로 받은 HTML에 무엇이 들어 있나
   - 서버 터미널에 무엇이 찍히나
   - 브라우저 네트워크 탭(정적 파일 제외)에 어떤 요청이 있나
   - 브라우저 콘솔에 어떤 로그가 어떤 순서로 찍히나
   - 질문: 서버가 만든 HTML에 게시글이 들어 있는 쪽은 어디인가. 브라우저가 `/data/posts.json`을 요청하는 쪽은 어디인가. `/csr`은 서버 렌더링을 안 하는 걸까?
2. **클라이언트 전환**. `/ssr`에서 게시글 하나를 클릭한다.
   - 네트워크 탭에 무슨 요청이 나가나. HTML 문서 요청인가, 아닌가.
   - loader는 어디서 실행됐나. 서버 터미널을 본다.
   - 없는 글 `/ssr/99`로 들어가면 HTTP 상태와 화면은 어떻게 되나. 클릭으로 들어갈 때와 주소창으로 들어갈 때가 같은가.
   - 질문: 상세 화면의 "목록으로"를 클릭하면 네트워크 탭에 무엇이 보이나. 게시글 제목 링크를 클릭할 때와 왜 다른가.

### 과제 B. 버그 하나 고치기

`/ssr`을 열면 화면은 멀쩡한데 브라우저 콘솔에 에러가 하나 있다.

- 원인을 찾는다. 에러 메시지가 힌트를 꽤 준다.
- 왜 화면은 멀쩡해 보이는지 설명한다. 멀쩡하면 그냥 둬도 되는 건가?
- 고칠 방법을 **두 개 이상** 비교하고 하나를 골라 적용한다. 고른 이유와 버린 이유를 적는다.
- 고친 것이 다시 깨지지 않게 테스트를 추가한다.
- 질문: 브라우저 없이 `curl`만으로 이 버그를 눈치챌 방법이 있나.

### 과제 C. 깨진 데이터

`public/data/posts.json`의 레코드 하나를 스키마(`src/common/schemas/post.ts`)에 안 맞게 바꾼다. 복구는 `git checkout -- public/data/posts.json`.

- `/csr`, `/ssr`, `/ssr/1`(정상 레코드)에 대해 HTTP 상태, 화면, 브라우저 콘솔, 서버 터미널을 표로 만든다.
- 질문: 어느 쪽이 서버 모니터링에 잡히나. 서버 로그만 보고 실패를 알 수 있나. 정상 레코드를 조회한 `/ssr/1`은 왜 그런 결과가 나오나.

### 산출물

`docs/01-render-flow.md`. 과제 A·C의 표, 과제 B의 원인·수정 비교, 마지막에 "다음에 SSR 디버깅할 때 볼 순서" 체크리스트 5줄 이내. 다 쓴 뒤 `debug/render-flow` 브랜치의 같은 파일과 비교한다.

## 시나리오 2 — 화면 개발 플로우 한 바퀴: 상세페이지 댓글 (`feat/comments`)

목표: 기존 화면에 하위 기능 하나를 붙이는 실제 개발 흐름을 처음부터 끝까지 한 번 밟는다.

범위: **정적 JSON 읽기만.** 작성·수정·삭제 없음. 백엔드·DB·resource route 없음.

### 단계

1. **데이터.** `public/data/comments.json`. 게시글과는 `postId`로 연결. 댓글이 하나도 없는 게시글을 최소 하나 남긴다.
2. **스키마와 타입.** `posts`가 한 방식 그대로 Zod 스키마와 타입을 만든다.
3. **조회.** CSR용 조회 함수와 SSR용 loader. SSR 상세 loader는 게시글과 댓글을 **어떻게 합쳐서** 내려줄지 정한다.
4. **컴포넌트.** 댓글 목록 컴포넌트. 빈 상태 포함. CSR 상세와 SSR 상세 두 페이지에 붙인다.
5. **테스트.** 조회 함수, loader, 컴포넌트, 페이지. 기존 테스트 패턴(`.claude/rules/testing.md`)을 따른다.
6. **브라우저 확인.** CSR 상세와 SSR 상세에서 네트워크 요청 수를 비교한다. 클라이언트 전환의 `.data` 응답 안에 댓글이 들어 있나.
7. **디버깅 적용.** 시나리오 1에서 만든 체크리스트로 점검한다. 댓글 데이터 하나를 깨뜨리면 게시글까지 안 보이나. 그게 원하는 동작인가.

### 관찰 질문

- CSR 상세에서 조회가 실패하면 화면은 어떻게 되나. 지금 코드를 먼저 읽고 예상한 뒤 실제로 깨뜨려 본다.
- 댓글 날짜를 표시할 때 시나리오 1의 과제 B가 다시 나타나나.
